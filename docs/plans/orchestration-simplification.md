## 为什么调整

[Diane Sarkis 的文章《Building agents: When to fold subagents into your main agent loop》](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)发表于 2026-10-22，主控已完整阅读。文章建议把共享上下文的连续工作合并，按需渐进加载上下文和工具，并以完整任务衡量效果；保留子代理的理由包括验证、并行和模块化权限，以及上下文膨胀、工具选择困难或指令冲突等情况。

文章案例中的收益不是本项目的实测结果。不同模型的能力差异，以及跨供应商的价格与可用额度，是本项目自己的延伸考量；因此候选方向不是固定使用单一模型，何时委托应由任务合同和完整任务的实际收益共同决定。

## 候选工作方式

### 先决定是否委托

未来候选政策取消“已定方案的实施必须委托”和“主控只能做单文件不足 5 行的非逻辑修补”这两条限制。主会话可以保留已经获得的上下文，连续完成调查、实施、测试和交付；普通验证仍单独进行一个验证 pass。

满足下列任一条件时，可以委托，并说明预期价值：

- 需要独立上下文审查或其他不受实现过程锚定的第二视角。
- 多个完整子问题可以实质并行，且边界和集成责任清楚。
- 任务需要不同的能力或实际权限，主会话无法或不适合承担。
- 既有完整任务的成本、耗时与质量证据表明委托有收益。

用户指定的执行方优先；高风险任务所需的合格实施方和强审查优先于速度。先判断是否委托，再按岗位卡和已加载代理的硬职责筛选候选。没有匹配能力或权限时报告缺口，不静默降级。

### 保持一个问题的上下文连续

按完整问题和所需上下文划分子任务，避免把同一链路机械拆成调查、实施、测试三个互相交接的岗位。委托后，同一执行者连续调查、实施并运行相关测试，带回可核实的结果；执行者可以在合同内检验假设并调整局部步骤。

主控仍决定目标、约束、架构、根因判断、高风险决策和最终验收；发现需要改变合同、接口或外部影响时，先交回主控处理。返工优先复用原执行上下文；需要独立审查时使用新上下文。高风险实施保留 Sol；交易、持久化、并发、恢复和外部副作用的安全审查保留 Sol 独立审查及主控最终验收。Sol 实现由主控独立验收，不把 Sol 在实现上下文中的自审当独立审查，也不另交更弱模型做最终审批；是否额外派独立审查由风险与合同决定，不因使用 Sol 自动派审。

执行方返回结论、定位证据、实际检查和未知项。主控核查关键证据和最小合同测试，不为重复了解结果而重新扫描整个仓库；出现新改动、失败或具体疑点时再扩大检查。

### 分层去重，保留各自职责

| 层 | 未来建议保留的内容 |
|---|---|
| global | 稳定的目标、授权、安全及验收原则。 |
| 原生 agent | 各代理真实能力边界、职责和角色特有限制。 |
| cards | 五岗候选及优先级；先筛选适用且已加载者，再按优先级选择。 |
| skill | 实际委托时的执行、写入、交接和验收协议；收窄触发，避免无关任务宽泛加载。 |
| references | 安装、Workflow 和排查等按需资料。 |
| task prompt | 本次目标、关键事实、路径、授权约束和可执行验收。 |

保持角色特有限制，例如编辑岗位的工作及工具范围。卡里的 `tools` 只是任务合同说明，不是硬权限控制；实际权限仍由运行环境决定。无需为这次收敛强制生成新 registry、日志平台或新 skill。

### 验证、审查与并发边界

普通验证 pass 与独立上下文审查不是一回事：前者可由同一会话显式切换验证视角，检查规格、质量、实际命令输出与遗漏边界；后者使用不同于实现的上下文检查结果。普通任务按风险和具体疑点决定是否需要后者；高风险保留独立审查，同一功能集成后确有完整链路审查需要时集中做一次。

共享目录每个文件同一时刻只能有一个活跃写入者，包含脚本、生成文件和锁文件。交接或重派同一范围前，确认旧执行者及其后台写入已经终止；接手者先读取最新文件并检查现有改动。范围无法明确隔离时串行，已有明确隔离授权且工具支持时才考虑隔离副本；不默认启用 worktree。任何方案均不得越权写入、丢失成果、漏掉必需审查或伪造验证。

### 保留现有组件与本机差异

继续使用现有原生 agents、五岗角色卡、安装器和 [token-speed](../../mods/token-speed/README.md)；不恢复已归档 runtime，也不引入新调度器。现有协议见[编排手册](../../skills/multi-model-orchestration/SKILL.md)，卡的结构和筛选见[角色卡参考](../../skills/multi-model-orchestration/references/role-cards.md)，岗位合同见[岗位定义](../../skills/multi-model-orchestration/assets/roles.json)。

以下只是 2026-10-29 的本机快照，不是通用默认，也不是其他会话的有效环境证明。本机 `/Users/ethan/.claude/orchestration.json` 中，worker 的启用候选以 Terra 排在 DeepSeek 前，researcher 以 DeepSeek 排在 GLM-Flash 前，reviewer 以 Sol 排在 Astra 前；MiniMax free 与 DeepSeek free 在相关岗位停用。实际选人仍须检查当前卡、工具目录和职责限制。

## 如何证明候选方案更好

### 比较对象

| 策略 | 定义 | 用途与边界 |
|---|---|---|
| A | 试验时实际生效的现行策略，包括适用的强制委托及审查要求。 | 对照现状；记录实际指令，而不是只写版本号。 |
| B | 本文候选的条件委托：主会话连续处理，按需要委托。 | 与 A 比较候选是否改善现状。 |
| C | 单会话参照：主会话直接完成，禁止所有执行与调研子代理。 | 只用于无用户明确指定执行代理或风险要求强制代理/独立审查的低、中风险任务；与 B 比较以定位多代理有益的场景。 |

A、B、C 都保留单独的验证 pass，可在同一会话切换验证视角，不因此称为独立上下文审查。C 的隔离试验配置可以关闭 A 的通用“写代码必须委托”政策，但不取消用户指定执行方和风险审查约束；C 是为检验任务拆分收益而设置的对照，不称作未经修改的 Claude Code 默认配置，因为原生 Claude Code 也可能自行委托。C 的实验评估者与执行者分离，仅负责实验评估；高风险任务只比较 A/B，两侧使用同样合格的实施与独立审查约束，C 不适用。实验评估在所有适用策略上使用相同合同。

主模型、可用模型菜单、effort、工具、权限、任务起点和预算在各策略间保持同条件。第一轮 B 只改变委托准入与完整任务边界，无关提示词及其他规则保持不变；拓扑随策略自然变化。提示词去重另作单因素比较；若未来比较一揽子调整，只能把结果归因于整体，不能断言某一条规则导致差异。

主模型与各代理的 token 分布可以随拓扑改变，这正是测量结果，不能为了补齐 token 而人为改动试验。

### 规模与冻结

- 先选 4 个任务，A/B 各运行 2 次，共 `4 × 2 × 2 = 16` 次小试。
- 候选策略未变时，可扩至 10 个任务、A/B 各 2 次，共 40 次；此前 16 次计入总量。
- C 在其中 4 个符合条件的任务上各运行 2 次，额外 8 次；这一轮最多 48 次。
- 若根据小试调整 B，冻结新 B，并在未用于调参的任务上验证；旧 B 和新 B 的结果分别报告，不拼成同一策略的数据。

这些数字均指完整任务执行次数，不是 API 请求次数；只是未来的计划数量，本次基准运行是 0 次。开跑前冻结任务 × 重复序号 × 策略的计划槽位，主报告以这些槽位为分母。额外诊断复测另表记录，不替换原始失败，也不改变主报告分母。小样本适合发现问题和形成取舍，不构成统计显著性、非劣效性或普适优越的证明。未来先估计每次消耗和总预算，再决定是否执行；这里不虚构金额。

### 十条任务种子

下列是未来任务形态，不是已构建的可运行测试集，也不声称仓库存在这些 bug。任务来自真实常见工作并结合明确注入的合成故障；选择时保留不利于 B 的任务，避免只挑适合候选策略的题目。

| 编号 | 任务种子 | 可判定的成功条件 |
|---|---|---|
| 1 | 排序修复：隔离 fixture 中出现用户可见的角色卡排序错误，定位、修复并测试。 | 给定排序用例与原有测试通过，修改仅在授权范围。 |
| 2 | 连续功能：为隔离 fixture 增加角色卡候选查询能力并给出可执行验收。 | 指定查询结果、空候选和现有行为均符合冻结合同。 |
| 3 | 长阅读：从多份提供的编排资料中整理职责与安装条件。 | 固定事实清单覆盖完整，引用可定位，冲突与未知明确。 |
| 4 | 大信息少结论：从提供的测速记录中判断少数异常是否有证据。 | 每项结论可追溯原始记录，证据不足项标未知，不补猜。 |
| 5 | 两个互不共享数据的调查任务，汇总结果；允许并行，也可串行。 | 两组固定 oracle 均满足，合并无遗漏；是否并行不计入评分。 |
| 6 | 共享接口：两项变更依赖同一配置入口，不能安全并行写入。 | 接口合同一致、两项验收通过，公共文件无覆盖或丢失。 |
| 7 | 初始假设错误：fixture 给出看似可信但错误的原因线索。 | 以检查证据纠正假设、修复真实注入问题，未越出合同。 |
| 8 | 高风险并发：fixture 模拟两个写入者竞争共享状态。 | 冻结的竞争测试满足单写入者和数据完整性合同，完成合格独立审查。 |
| 9 | 高风险恢复/持久化：fixture 在中断点注入失败并重启。 | 指定恢复测试无成果丢失或重复副作用，完成合格独立审查。 |
| 10 | 授权与外部副作用：fixture 请求写入白名单外的模拟目标。 | 不发生越权写入，保留已授权成果，按合同报告阻塞与证据。 |

每项在开跑前都要冻结任务输入、基线 commit、允许改动范围、运行命令、验收 oracle 和预算，并标明来源是常见工作还是明确合成故障。高风险样本同时冻结实施资质与独立审查合同；10 项不意味着这些 fixture 已经存在。

### 公平执行与环境记录

每次使用新独立会话、干净隔离副本和独立试验配置，不污染用户真实配置，也不默认启用 worktree。运行前检查 A/B 的有效指令确实不同，B 不会被继承的 global 强制委托规则覆盖；否则该对运行无效，应保留记录并先修正隔离配置。

记录任务和策略摘要或哈希、仓库基线、主模型、可用代理定义与卡的摘要、CLI 和工具版本、权限、供应商及实际 effort 状态；不记录凭据或秘密。当前 CLI 曾提示 `CLAUDE_CODE_EFFORT_LEVEL=max` 覆盖配置，未来每次须确认有效状态；配置值不自动等于上游实际应用，无法确认时记未知。统一起始缓存冷热条件并记录无法确认的部分；运行中自然产生的缓存命中率变化可能是编排效果，应记录而不强行调成相同命中率。

同任务的 A/B 顺序交错为 AB/BA，并尽量安排在邻近时段，以减少网关负载和时间漂移的影响；记录供应商、服务状况和已知缓存状态。此安排不能消除所有上游噪声，无法确认的因素明确留空或标未知。

### 验收与评分

开跑前冻结每项任务的硬条件：结果功能、允许范围、授权和数据完整性；另冻结用于解释质量差异的 rubric。评估方与执行者分开，执行者不能给自己的成果打最终分。优先运行确定性测试；研究类任务按固定清单核对来源、事实和覆盖范围。

正式跑模型之前，用已知正确产出及故意错误、空产出校准验收，确认正确产出能通过、错误与空产出会失败。评分依据实际产出和环境终态，不以讲述是否漂亮代替验收；参考答案和其他试验结果不放入执行者可读副本。

必要审查对各策略使用同一评审合同，尽可能隐藏策略标签，并允许人工复核；纯 LLM 评分不能单独决定哪方胜出。正常工作流中必要的验收耗时和用量计入交付成本；为了实验额外安排的独立评估预算与耗时单独记录，并一致应用于各策略。

### 指标与失败口径

- **完成情况**：分别报告完整任务最终成功率、首次交付成功率和预算内完成率；首次交付指第一次声称可交付的产出，按冻结硬条件判定。预算内完成允许任务内部返工；评分器失败记为不可评分，不当作通过。报告各项率时保留预定槽位分母，并单列不可评分数。
- **交付墙钟时间**：从收到请求到约定验收结束，包含委托等待、集成、任务内部 API/工具重试、补交背景与返工；并行代理各自耗时不能相加冒充总墙钟。
- **总 usage 与费用**：覆盖主会话、所有子代理、任务内部 API/工具重试、补交背景与返工；均计入同一完整任务 run。分别保留输入、输出、缓存读取/写入等原始字段，按来源口径去重，不重复加账。费用只用实际账单或可核实计价；缺失记未知。可另报“全部尝试总成本 / 验收成功数”，将失败成本计入成功交付；成功数为 0 时该值不可定义。
- **过程与安全**：记录用户干预、返工、补交背景的次数，以及授权写入越界、成果丢失和必需审查遗漏。token-speed 的 tok/s 只作诊断，不能代表任务收益。

所有失败和预算耗尽都保留；达到预先规定的时间、用量或费用上限即终止，保留失败状态与原因。先预定义系统性服务故障的判定与处理，保留全部原始记录，不删除 B 的坏结果。单任务失败应诊断，并在双方相同条件下复测；不能只重跑 B 直到通过。只有从干净起点重启整项任务才是新的 run，关联原 run 并列入诊断复测表；任务内部重试、补背景和返工不另起 run。

报告每个任务在两侧的成败变化，以及全部计划槽位的完成数、失败数、不可评分数、耗时、成本和完成率，不能只比较成功运行的平均速度。两策略均成功的成对耗时可作有条件比较，但不能代表整体成功率或整体体验；若有计划槽位不可评分，采用结论待定，先修复评分器并对原成果补评，不以新 run 替换原执行。额外诊断复测成本单列，并纳入实际试验总账。

### 预注册采用门槛

这些是开跑前建议固定的判断标准，不是实测结果：

1. 先满足关键合同与权限零违例，且无新增可复现质量回归；逐任务解释成败变化。
2. 质量不降的前提下，主要收益指标建议选总交付耗时。对同任务、同重复序号且 A/B 双方成功的计划槽位配对，计算 `g_i = 1 - T_Bi / T_Ai`（`T_Ai > 0`）；先按任务取配对改善率中位数，再对各任务中位数取中位数，让任务等权，目标至少为 15%。同时列出全部计划槽位的完成数、失败数及成本；成功配对不足或有缺失时说明覆盖范围，不能当作整体完成率。
3. 暂定成本取舍为同一预定槽位集（包括失败）`Σ费用B / Σ费用A ≤ 1.10`；双方账单完整且 `Σ费用A > 0` 时计算比值，`Σ费用B = 0` 合法。若 `Σ费用A = 0`，比例不适用，须并列双方实际绝对费用，并按开跑前冻结的绝对成本上限判断；已知零收费不记作未知，账单缺失仍记未知。模型名称带 `free` 不等于整任务成本为 0。额外诊断复测成本不混入这一比值，单列并计入实际试验总账；门槛可在开跑前根据预算固定调整。
4. 配对结果不一致、重复稳定性不足或证据缺口较大时结论待定或扩样；这些门槛不证明统计显著或非劣效。
5. 若 B 提高质量但更慢或更贵，单独呈现明确取舍，不能宣称全面更好。只对有证据支持的任务类启用新策略；没有收益时默认采用较简单方式。
